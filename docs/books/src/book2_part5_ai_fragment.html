Part V

Future evolution

How SpeakCraft could add artificial intelligence later — optionally, on the device first, and without weakening the two principles the product is built on: honest feedback and private by default. This part is a design for decision, not a plan. Releases R1 and R2 ship with no AI.

Chapter 20Future AI implementation (design)

The Product Owner asked for a system design for future AI. This chapter summarises it. The design adds an optional AI layer after the deterministic feedback pipeline. That layer can only add a separate, clearly labelled suggestion. It never changes a metric, a mistake found, a coach tip, a pass mark, a streak or progress. It starts on the device, and it uses the cloud only after a separate consent, a privacy review and two further decisions.

Status: proposed for R3+ — not in R1/R2; the app works fully without AI Everything in this chapter is Proposed and R3+ conditional. It becomes eligible for planning only after the new decisions D-37…D-41 are recorded, ADR-016 is approved, a privacy review under SEC-01 §9.7 is completed and the data-safety inputs are updated. D-04 still recommends removing cloud AI from R1 (ADR-003), and the non-goals NG-01 (cloud AI or LLM generation), NG-02 (AI tutor or chatbot) and NG-03 (phoneme scoring) stay in force for R1 and R2. Every new dependency named here needs its own ADR. Values marked † are placeholders to be tuned by spikes.

ARC-06 v0.1 header and §1; ADR-016; ADR-003; RD-16 §4; Stage A brief ("Do not make large LLMs mandatory"; "Cloud AI must not be introduced without explicit product authorization, privacy review and a secure implementation design").

20.1 What this design is, and what it is not

ADR-003 removes the dormant cloud-AI code from the current app and says that any future AI feature needs a new ADR, a privacy review and explicit authorisation. ARC-06 is the secure implementation design that such an authorisation would review. It answers three questions: which AI features would be worth having, how they could be added without breaking honesty or privacy, and what cheap preparations R1 and R2 could make so that adding AI later is not a rebuild.

ARC-06 is

  • A conditional target architecture for R3 and later
  • An optional augmentation layer after the deterministic pipeline
  • Advisory text labelled "AI suggestion" that the user can ignore
  • On-device first; cloud only after consent, review and D-38/D-39
  • The owner of proposed IDs until other documents adopt them

ARC-06 is not

  • A plan, an R1/R2 epic or a commitment
  • A replacement for ARC-05 local intelligence
  • A source of metrics, scores, pass/fail, streaks or progress
  • A mandatory large-language-model dependency
  • A change to any existing document (amendments follow approval)

Why UC-AI-1 is not "AI judging the user"

Transcription is input, not judgement. The platform recogniser already plays that role (ADR-009). An on-device AI recogniser would plug into the existing recognition session as one more backend (CMP-92). It would feed the same evidence gate, metric engine and rule engine, which stay deterministic. Two conditions keep it honest. First, it must return verbatim recognition: any formatting or "clean-up" mode stays off, because a model that turns "he don't" into "he doesn't", or drops "um", would hide exactly the mistakes the coach exists to find. Second, the attempt records which engine produced the transcript (transcript_source), so a trend change caused by an engine switch can be recognised. SPK-03 therefore measures an error-preservation rate and a filler-retention rate as well as word-error rate. On 2026-11-21 the GenAI speech-recognition page listed en-US, but not en-GB, en-IN or en-AU, among its English locales. SpeakCraft offers all four, so this is risk RSK-27.

ARC-06 §3.2 UC-AI-1; ADR-009; VERIFIED on the ML Kit GenAI speech-recognition page, 2026-11-21 (alpha API; basic mode on API 31+, advanced mode on Gemini Nano devices).

UC-AI-3: "Possible" means possible

The deterministic rule engine ships only rules with precision of at least 0.90 (NFR-QUAL-003), so it misses many errors. An on-device proofreading model catches more, but with less certainty. The design keeps the two apart. The transcript is proofread, punctuation and capitalisation changes are discarded, and each remaining change becomes a "Possible wording" item in the AI card. These items never enter "Mistakes found", are never counted in M-GRAM, never raise ISSUE_GRAMMAR_POSSIBLE and never affect word-stage 4. Where a deterministic rule already flagged the same span, the deterministic item wins and the AI item is removed.

20.3 Target architecture

The existing pipeline runs first and completely. Its EvaluationResult.Valid is saved and the result screen is rendered before any AI work starts. The AI layer receives a read-only copy through a seam called FeedbackEnhancer. In R1 and R2 that seam is a no-op. The layer can do one thing only: add a separately labelled card. No arrow returns from the AI layer into the pipeline.

20.4 Provider chain and fallback

For each call the policy gate walks a fixed chain. "No AI" is the starting point and the default. On-device AI is tried only if the user opted in and the model is ready. The cloud is reached only in option C, only for a signed-in user who consented to that specific feature, within quota and with an attested app. Whatever path is taken, the output passes the validator or is dropped. In every case the deterministic result is already on the screen.

20.5 Honesty mechanics: how the validator keeps AI truthful

Prompt instructions ask the model to be honest, but the design does not trust them. Every output is checked mechanically. If one rule fails, the whole output is dropped — never edited into shape.

SchemaOutput parses against the feature's JSON schema (for tip rewording: tipText ≤ 280 chars †, basedOnIssue, at most one quote)Free text, extra fields
GroundingAfter normalising case and punctuation, every quote is a contiguous run of the transcript's tokens; any quoted text outside the quote field is rejected"You said 'I basically managed it'" when the user said "I managed it"

The augmentation layer leaves the eighteen existing entities untouched; the attempt record stays immutable and deterministic. Export. The ARC-03 export gains optional fields only, so formatVersion stays 1. Deletion. No-account mode (D-41 recommendation) On-device features are available after the user opts in, because they make no SpeakCraft network call and keep SEC-REQ-02 true. Cloud AI is not offered without an account, for four reasons: the no-account mode promises network silence; per-user quotas and abuse controls need an identity; a cloud call would also start Firebase traffic (App Check, Installations); and the user who chose the most private mode should keep it. The deterministic feedback is complete without AI anyway.

Cloud consent (modelled on the T3a disclosure)

Cloud use needs its own consent for each feature, separate from the on-device opt-in. It follows SEC-01 §7.3 element by element. The thirteen mandatory elements (CA-1…CA-13) cover: what is sent (the transcript text, the question and the names of the checks; never audio or account data); to whom (the provider, whose terms apply); when (only after an attempt, only while on, only when signed in, never in the background); why; what SpeakCraft keeps and what the provider keeps (retention and "not used for training", as verified on a stated date — if this cannot be said truthfully, cloud AI does not ship); that AI can be wrong and never changes results; the alternatives; immediate withdrawal; equal-weight choice buttons with nothing pre-selected; timing (never mid-recording, never in onboarding); a local consent record; and accessibility.

20.11 Cost and operations

On-device inference has no per-call server cost (VERIFIED on the ML Kit GenAI page). Its costs are battery, model storage, device fragmentation and the churn of alpha and beta APIs. Cloud cost depends on tokens. The design states a formula, not prices, which are taken from the provider's price list at decision time.

Monthly cloud cost ≈ U × A × r × [ (T_in × P_in) + (T_out × P_out) ] + C_fixed

U  = signed-in users with the cloud feature consented      A = eligible valid attempts per user per month

ARC-06 §14 (proposed additions to the PLN-04 RAID log, which ends at RSK-18).

In one paragraph SpeakCraft can add AI later without becoming a different product. The deterministic coach stays the source of truth, and AI may only add a separate, labelled, grounded and rateable suggestion. The order is on-device first, starting with better transcripts, then reworded tips and "Possible" wording suggestions. Cloud content feedback comes only after a separate consent, a privacy review, verified provider terms and an attested Play build. Every step has a gate and a kill switch. Nothing changes in R1 or R2 except, if the Product Owner agrees, a few no-cost seams.
