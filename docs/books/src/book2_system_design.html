What exists today vs what is planned

Exists today (EXISTING). A single-module Kotlin and Jetpack Compose app of 106 files (about 48,900 lines), built in three days of AI-agent commits. Its core promise does not work by default: no transcript is produced unless live transcription is found and enabled, and then only the first utterance is captured. Several scores measure something other than their label. Speaking-session saves are rejected by the Firestore rules, account deletion is unreachable, and CI can publish debug-signed builds without running a test.

Exists from Stage A. Documentation only: an audit of the current app, the product direction, requirements, UX design, architecture, security design, test strategy, delivery plan and this book.

Planned (PROPOSED). The rebuilt app described here. No part of it has been implemented, compiled or tested. Implementation starts only after gate G4 and an explicit "start Stage B" instruction from the Product Owner.

What will be built

  • One Android app, no custom server. Kotlin, Jetpack Compose and Material 3 in a single :app module, organised by feature. Firebase Auth, Cloud Firestore and App Check are used only by people who choose to sign in. Background work runs on the device with WorkManager.
  • The phone is the system of record. Room databases hold all learning data; Firestore is an optional backup and sync target that receives metrics only — never audio, file paths or transcripts.
  • On-device, deterministic feedback. Platform speech recognition in four capability tiers feeds an evidence gate, a catalogue of labelled metrics (Measured or Estimated), qualified language rules, and a feedback composer that lists the mistakes found, with evidence, and coach tips chosen from the content pack. When evidence is insufficient the result is Inconclusive. No cloud AI is used.
  • Four tabs. Today · Practice · Words · Progress, with one full-screen session player shared by every speaking task.

How it will be delivered

  • R0 Foundation — safety fixes, CI gates, removals, data foundation and the speech spike: about 38–55 engineering days †.
  • R1 Core loop MVP: about 107–156 engineering days †, plus about 38 person-days † of content verification by the Product Owner in parallel.
  • R2 Depth (role-play, check-ins, notebook and quiz, inbox, content): about 31–46 days †. R3 is conditional (store launch, video self-review, recognition research).

Part I

System design and architecture

How the rebuilt SpeakCraft app is structured: its context and layers, the Android frontend, the managed cloud services it uses instead of a backend, the on-device speech and feedback pipeline, the data model, its integrations, its environments, and its security and privacy controls.

Every item in this part is Proposed — awaiting approval at gate G3. Nothing has been built.

Chapter 1Architecture overview

SpeakCraft will be rebuilt as a single-module, offline-first Android application on its existing technology stack. The phone is the system of record. Firebase is an optional backup and sync target for people who choose to sign in. All speech processing happens on the device.

Status of this chapter The target architecture is Proposed and awaits approval at gate G3. Each ADR is approved or rejected individually. The current code is described as EXISTING only to explain why a change is proposed.

1.1 System context

Figure 1.1 shows everything SpeakCraft talks to. The app runs entirely on the learner's phone. It uses Android platform services for speech, audio, text-to-speech, background work, notifications, sign-in and file export. It reaches the internet only in three situations, each one chosen by the user: signing in and syncing (Firebase), online transcription on phones without an on-device recogniser (tier T3a, after explicit consent), and opening a source-video link in the YouTube app or a browser.

ARC-01 §1, §12; ARC-04 §1 (P-1…P-6), §3.9; SEC-01 §4.1

There is no custom backend SpeakCraft has no server of its own and none is proposed: no REST or GraphQL APIs, no Cloud Functions and no admin endpoints. The device talks only to managed services through their SDKs — Firebase Authentication and Cloud Firestore, protected by Firebase Auth identity and security rules — and only when the user is signed in. Any server-side component would need its own ADR, a privacy review and Product Owner approval (ARC-04 P-1, P-5).

1.8 Technical risks the architecture must absorb

  • RSK-01 Recognition quality varies across devices. On-device recognition may be unavailable or poor on many target phones. Spike SPK-01 decides tier T1/T2 behaviour before the R1 build; the tier design, consented online mode and honest audio-only mode limit the damage.
  • CL-72 java.time on Android 7.x. The current code uses java.time with minSdk 24 and no desugaring, which is likely to crash on API 24–25. D-14 recommends raising minSdk to 26; the domain layer uses epoch milliseconds and date keys so it is safe either way.
  • Storage Recordings need AAC transcoding. Thirty days of daily 16 kHz WAV recordings would take about 290 MB, so the transcode is now mandatory (ADR-015 revision); encoder reliability on API 24–28 is checked in SPK-01.
  • Lifecycle Rotation must not stop a recording. Capture stops when the app goes to the background, but not on configuration changes (Chapter 2).
  • Platform TTS on API 30+ probably needs a <queries> entry for the TTS service, in addition to the recognition service; SPK-01 confirms it.
  • RSK-18 / RSK-03 Wrong or over-reported mistakes. Issues are raised only beyond noise bands; grammar rules ship only with ≥ 0.90 precision †; golden tests and the "Was this accurate?" rating monitor quality.

Chapter 2Frontend: the Android app

The app is one Activity hosting a Compose navigation graph. Screens render a single immutable state object and send intents to a ViewModel; ViewModels call domain engines, speech services and repository interfaces; a process-wide container wires everything together. This chapter describes that structure, the session player at its centre, and the rules for threading, lifecycle, errors and feature flags.

2.10 Coding rules that protect honesty

  1. A metric without inputs is null with a reason. Default, baseline, clamp-to-plausible or placeholder values (patterns such as ?: 0 or ?: 62) block a code review.
  2. Recogniser confidence is used only when the recogniser supplies it.
  3. Every metric shown carries its label. "Recognised as intended" is never called pronunciation.
  4. Feedback, issues and tips are deterministic functions of stored inputs. The only "randomness" is a specified stable hash that varies tip wording reproducibly. No generative or cloud model is used.
  5. Counters are derived from facts; nothing increments on navigation or taps.
  6. Time comes only from the injected Clock and DateKeyProvider; the local date key is captured at event time and never recomputed.
  7. Files stay under 600 lines unless justified; all strings and plurals live in resources.

3.3 Cloud Firestore: the named database as a sync target

  • One database, one subtree. The existing named database is retained. Only the signed-in owner's subtree users/{uid} exists in the target schema, holding six document types (Chapter 5). Shared, admin and release collections are frozen in R0 and removed later.
  • One caller. Only FirestoreRemoteDataSource (CMP-52) issues Firestore calls, and only from the sync worker, the sign-in flow, the deletion executor and the legacy migrator. Repositories write Room rows and outbox entries; ViewModels never touch Firestore.
  • No listeners. The 16 unbounded snapshot listeners started today are replaced by bounded, paginated pulls keyed by a server-timestamp watermark.
  • No trusted aggregates. Streaks, totals and scores are never stored in the cloud; they are derived on the phone from immutable facts. A user who forges facts affects only their own data.
  • Memory-only SDK cache (RECOMMENDATION). Room is the source of truth, so the SDK's on-disk cache would be a second, unencrypted copy that can diverge and could grow to about 100 MB (INFERRED). Retries belong to the outbox, so a write counts as done only when the server confirms it.

Indicative cost. ARC-03 estimates about 15 writes and 40 reads per active user per day, roughly $0.0015 per user per month at list prices, plus 4–6 MB of storage per user after two years † (INFERRED; prices vary by location, and the free daily quota may not apply to a named database).

Chapter 4Local intelligence (speech and feedback)

The heart of SpeakCraft is a single on-device pipeline that turns a spoken attempt into a transcript, three labelled metrics, one strength, the mistakes our checks found — each with evidence — and coach tips for the next try. It uses Android's own speech recogniser and deterministic, versioned rules. It uses no cloud AI and no language model, and when the evidence is too weak it says Inconclusive instead of guessing.

Validation still to come The tier design must be validated on real devices by spike SPK-01 before the R1 build, and grammar rules ship only after the SPK-02 corpus shows ≥ 0.90 precision †. 4.4 Capture and recognition

  • Capture. AudioRecord with the voice-recognition source (falling back to the microphone source), 16 kHz, mono, 16-bit PCM in 20 ms frames. Frames fan out to the WAV writer, the feature extractor and, in T1, a pipe to the recogniser. Fixed ring buffers keep memory constant whatever the attempt length. Audio focus is requested as exclusive; its loss interrupts the attempt, as does the app going to the background.
  • One recognition session per attempt, created on the main thread and released in finally. T1 uses a segmented session over the audio pipe. T2 and T3a restart listening within 150 ms † when a segment ends and stitch segments with de-duplication of overlapping words; results arriving after Stop are accepted only for the active segment, which fixes today's duplicated text.
  • Error classification. "No match" and speech time-outs mean no text for that segment (not a capability failure); network errors in T3a let the attempt continue without a transcript; a busy recogniser gets one retry, then audio-only for that attempt; a revoked permission interrupts.
  • Confidence comes from the recogniser only when it supplies it; otherwise it is null, never a constant.
  • Punctuation independence. Formatting is requested where supported, but no rule or metric depends on punctuation; any sentence-level heuristic uses pause timing.
  • Language packs (API 33+). Installed, pending and supported languages are read from the platform; "Install offline speech" calls the platform download. The app manages no model files of its own.

4.7 Rules and the feedback composer

Rule qualification (SPK-02). Each grammar rule needs a corpus of at least 30 positive and 30 negative examples written as unpunctuated, lower-case, recogniser-style text, including the false positives found in the audit. A rule ships only with precision ≥ 0.90 †; recall is reported but not gated. Expected survivors include unambiguous third-person agreement ("he don't"), "more better", "didn't went", common article errors with explicit vowel-sound lists, double negatives and a wrong past participle after "have". Run-on, sentence-length and "a lot of → many" rules are dropped. At most two grammar observations are shown per attempt.

  1. Candidates are content-pack tips whose triggers match the attempt: an issue code, a metric and band, a template, or a technique ID.
  2. They are ranked by trigger specificity (issue code > metric band > technique > template), then by the tip's priority, then by a stable hash of tipId + attemptId. The hash varies wording across attempts while staying reproducible.

5.5 Sync and conflict rules

  • Local first. Every write goes to Room in one transaction and returns immediately; each syncable change adds or coalesces one outbox row (ADR-014).
  • Upload. The sync worker drains the outbox in order — meta and purges, profile, attempts, events, words, plans, deletes — when signed in and online. Facts are created in batches; a retried create that the rules deny is checked with a server read and acknowledged if the identical document already exists, so retries never duplicate. Mutable documents are written in a transaction that reads the server copy, applies the merge rule and writes the result. Outbox rows move through PENDING → IN_FLIGHT → acknowledged, with FAILED and back-off, and DEAD (with a user-visible Retry) after repeated failures.
  • Pull. At sign-in, at app start when online, after an upload run and on manual Retry, the worker reads meta/sync and the profile, then pages through attempts, words, plans and events changed since a per-collection watermark (minus a 60 s † overlap), 200 † documents per page, merging each page into Room in one transaction. Facts are pulled by syncedAt, mutable documents by updatedAt.
  • Markers. Deletions are invisible to watermark pulls, so "Clear history", "Reset vocabulary" and account deletion write a marker in meta/sync before deleting cloud documents; other devices apply the marker on their next pull and do not re-upload purged items.

Techniques and tips

The single principal is request.auth.uid. The app builds paths only from the signed-in user's uid, never from input or intent data. 8.6 Backup policy (D-23)

The recommendation is include-only backup: Android cloud backup and device-to-device transfer carry only learning.db (learning progress and synced preferences) and the settings DataStore. People without an account therefore keep their progress when they change phones, while sensitive voice data never leaves the device. Disabling backup altogether was rejected because no-account users would lose everything on a phone change — and device transfer still happens for apps targeting API 31+ unless excluded, so extraction rules are needed either way.

8.7 Deletion

Account deletion is a client-side cascade with re-authentication, verification and resumable state — there is no server-side function to do it. Each phase is persisted in ENT-18 before its side effects count as done, and every step is idempotent, so a resume repeats at most the current phase.

PhaseAction
CONFIRMED → REAUTHENTICATEDExplicit confirmation online; Google account chooser; the uid must match, otherwise nothing is deleted
MARKER_WRITTEN → SYNC_STOPPEDA server-timestamped deletion marker stops other devices from uploading and offers them "Finish deleting account"; the sync worker is cancelled and the outbox cleared
CLOUD_SUBCOLLECTIONS → VERIFIEDAttempts, events, plans, words and legacy subcollections deleted in pages of 400 until empty; then each collection is confirmed empty with a server read
CLOUD_PROFILE → AUTH_DELETEDMeta and profile documents deleted; then the Auth user (re-authenticating again if the platform demands a recent login)
LOCAL_WIPED → DONEFull local wipe including Firestore persistence and credential state; the app returns to first run

If the process dies, the next launch shows a blocking "Finishing account deletion" screen and resumes; offline, it waits for a connection. Other data-rights actions follow a wipe matrix: Clear history removes attempts, metrics, plans, session events, transcripts and recordings locally and in the cloud (marker first); Reset vocabulary removes word progress, reviews and word events; Delete local data wipes everything on a phone without an account.

8.8 Logging and diagnostics

  • All logging goes through AppLogger; a CI check fails on any direct android.util.Log or println. Release builds drop verbose, debug and info levels and redact warnings and errors.
  • Never logged: transcripts and partials, audio, email, display name, uid, any token, Firestore paths containing a uid, file paths containing a profile id, consent details. A redaction filter replaces emails, uid-like tokens, JWTs, users/… paths and UUIDs, and strips URL query strings.
  • Events are enumerated codes with non-personal parameters, for example SYNC_UPLOAD_FAILED{collection=attempts, code=PERMISSION_DENIED, attempt=3}.
  • A rolling, PII-free diagnostic log (2 × 256 KB, 7 days †) stays in no-backup storage and is shared only from Settings → About → "Share diagnostics" after a preview. Crash reporting relies on this log and Play vitals; Crashlytics would need separate, opt-in approval (D-13).

A11Y-01 sets the target: WCAG 2.2 Level A and AA applied to a native Android app, interpreted as W3C's guidance for non-web software describes, plus Android-specific requirements (TalkBack, Switch Access, 200 % font scale, 48 dp targets). Two AAA-level behaviours are adopted because they matter here: animation from interactions can be removed, and targets are 48 dp. A release may say it "meets DES-07" only after the release test pack has been executed on the reference devices with captured evidence and every deviation approved at gate G6; until then the status is "target", not "conformant". This is not a legal conformance claim.
