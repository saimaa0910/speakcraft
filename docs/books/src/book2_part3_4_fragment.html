13.2 Definition of Ready and Definition of Done

Two short lists protect the plan. The Definition of Ready stops work from starting before its decisions exist; the Definition of Done stops work from being called finished before it is evidenced. PLN-05 is authoritative for both; USER_STORIES §2.3 repeats them in story terms.

Definition of Ready — a story enters a sprint when

  1. The linked SRS-FR or SRS-BR and the FS acceptance criteria exist.
  2. The ADRs and decisions it depends on are approved.
  3. A design is available for UI work (DES-03, DES-06).
  4. The test approach is known: TST-01 level and fixtures.
  5. It is estimated at 5 days or less; otherwise it is split.

The story view adds: open decisions affecting the story are listed, and dependencies are approved or stubbed.

Definition of Done — a story or epic is done when

  1. The code implements the referenced SRS-FR/SRS-BR and passes code review against the ARC-02 conventions.
  2. Unit and Robolectric tests were written alongside the code; all CI gates are green (build, unit, Robolectric, lint, rules tests where relevant).
  3. FS/US acceptance criteria are demonstrated, with evidence attached (CI link, screenshots or recordings).
  4. Accessibility checks for new UI (DES-07) and the honesty checklist (TST-01 §9) pass.
  5. No new Critical/High defects; known issues are logged.
  6. Documentation is updated: the authoritative document and GOV-01 traceability.
  7. Feature-flag state is documented; no dead code is left for removed features.

PLN-03 §2 (Ready); PLN-05 §6 (Done); USER_STORIES §2.3.

At epic level, "done" is tested at gate G5: the epic's FS test cases are implemented and Passed in CI with the run URL, new UI has passed the automated DES-07 cases and the honesty-checklist items for the touched screens, GOV-01 rows are updated, and no S1 or S2 defect is open in the epic (TST-01 §10.4).

Chapter 16Testing and quality assurance

Quality in SpeakCraft means more than "it does not crash". The product's promise is honesty: no number, label or status on screen that is not backed by evidence, no audio leaving the device by default, and no user data lost. The test strategy (TST-01) is built around proving those promises with evidence rather than asserting them.

Deliverable status — Test reports Not yet produced — created in Stage B after approval (gate G4). No test report exists. Stage A executed no build and no test, so every one of the 510 planned test cases is Not run. The existing repository contains 161 JVM and Robolectric tests, but none has ever run in CI, and the documented "161 passed" in an old report cannot be verified.

How reports will be produced. Every pull request run publishes JUnit XML/HTML, lint SARIF, coverage, the rules-coverage report and the traceability report as CI artefacts. At the end of each epic these become the epic test report for gate G5. For each release, manual and device runs are recorded in test-run records (TRRs) and combined into the release-candidate test report and the UAT report for gate G6. The template is in §16.14.

Acceptance. A test is Passed only when it was executed and its output is linked. Release exit follows TST-01 §10.3; the Product Owner signs the UAT report at G6.

How the rule-precision gate works

  1. A rule registry lists each rule with id, version and status shipped or candidate; only shipped rules can run in production.
  2. Precision = true positives ÷ (true positives + false positives); recall is reported, not gated.
  3. CI fails if any shipped rule has fewer than 30 positive or 30 negative examples, or precision below 0.90 †. The Wilson 95 % lower bound is shown for information.
  4. A failing rule is demoted to candidate through a reviewed code change.
  5. The grammar issue ISSUE_GRAMMAR_POSSIBLE can only come from a shipped rule, so mistake detection inherits this gate; at most two observations per attempt, worded as "Possible issue".

Mistakes found and coach tips

Golden tests map fixed transcripts and metric sets to the expected issues and tips. They assert that an issue is raised only when its source metric is non-null and outside its target band by more than the metric's noise band (boundary fixtures sit at the edge plus the noise band, just beyond it, and at null); that each issue carries its evidence and label; that issues are ordered by priority with the first three shown; that an Inconclusive attempt shows the gate reason and no issues; that tip selection ranks by trigger specificity, then tip priority, then a stable hash of tip id and attempt id — so the same attempt always gets the same tips; that a no-issue attempt shows "Our checks didn't find issues in this attempt", the coverage note, the strength and exactly one general tip; and that each tip links to its technique and, where provenance exists, to the specific source video.

Known gap before goldens can be fixed ARC-05 defines a target band only for M-WPM and gives no noise band for several metrics that raise issues, and its priority table omits some issue codes. Boundary goldens for ISSUE_TOO_SHORT, ISSUE_HEDGING_HIGH, ISSUE_FILLERS_HIGH, ISSUE_PAUSES_LONG, ISSUE_LOW_VARIETY and ISSUE_TOO_QUIET cannot be written until these values exist (TST-01 §17 issues 20–21; risk TR-21).

17.7 Versioning

version.properties at the repository root holds only versionName (SemVer, optional -beta.N). Gradle computes versionCode = MAJOR × 1,000,000 + MINOR × 10,000 + PATCH × 100 + B, where B is N for a beta and 99 for a final release. A release PR bumps the file and adds the CHANGELOG section; the tag is created on that merge commit and release.yml asserts tag = file. A versionCode is never reused.

A final release is always greater than its betas, and the scheme is greater than any legacy code (2 + run number), so in-place upgrades from release-signed legacy installs stay possible if D-15 keeps the applicationId. 18.5 Rollback plan

Android cannot downgrade an installed app, and Room migrations are forward-only, so "rollback" mostly means stopping the spread of a bad build and fixing forward quickly.

LayerStrategy
Android appPlay: halt the rollout, then ship a fix-forward hotfix or a "rollback build" — the previous good code rebuilt with a higher versionCode. GitHub interim: mark the release "Do not install" in its notes, remove the asset or revert it to prerelease, and publish the hotfix.
Firestore schemaChanges within a schema version are additive only; a breaking change bumps schemaVersion and rules accept both versions for at least two releases; fields that supported versions read are never renamed or removed; rules accepting old and new are deployed first, then the app; a client that sees newer data than it understands stops uploading and asks the user to update.
Firestore rulesKeep the previous ruleset id; roll back by redeploying the previous tagged firestore.rules. A rules rollback must not re-open retired legacy paths.
RoomMigrations are never destructive; downgrade is not supported, so rollback means fix forward.
Feature flagsCompile-time, so disabling a shipped feature needs a new release. Mitigation: ship risky features off in release and on in beta first. A remote kill switch would need Remote Config — a new dependency and an ADR — and is not proposed.

Hotfix process

  1. Open an incident issue with the severity (S1: privacy leak, data loss, crash on launch, security vulnerability, sign-in broken for everyone — fix released within 48 h †, rollout halted at once; S2: a core-loop feature broken for a segment — next patch within 7 days †; S3: normal release train).
  2. Halt the rollout or mark the GitHub release.
  3. Fix on a branch from main; if main contains unreleased risky work, branch hotfix/x.y.(z+1) from the release tag and cherry-pick back afterwards.
  4. Open a PR with the same required checks — no bypass.
  5. Bump PATCH and update the CHANGELOG.
  6. Tag, run release.yml, get environment approval.
  7. Write a post-incident note within 5 working days: cause, detection, prevention, test added.

Broken source-video links

A source video can be removed or moved after an item ships. The existing rules already cover this case: the link-out is checked on a device at every RC (TC-CONT-007, CC-05), and the own-words spot check opens each sampled link at its timestamp (TC-CONT-006). A link that no longer opens the specific video fails the content-compliance checklist, which makes it an S1 item: it is set back to PENDING_REVIEW and removed from the release, or the release is held. The fix repeats CNT-01 steps 1, 2 and 4 (find the video, confirm the timestamp, update provenance with a new verifiedOn), takes a second review, bumps packVersion and ships in the next release. If no specific video can be found, "no match, no ship" applies.

Growing the curriculum

R1 ships the verified existing items plus the highest-value techniques (about 15 †, D-36). Further channel videos are catalogued with the CNT-01 template and released as content updates in R2 (T-09.8, EP-23: +10 activities per track, +300 words), so the Product Owner's aim of covering all techniques is reached in steps rather than squeezed into R1 (RSK-17).

19.6 Evaluation-rule updates

  • Every change is versioned. evaluationVersion is the semantic version of the rule set and metric definitions, stored with every attempt and listed in a changelog. Thresholds live in EvaluationConfig, versioned with it.
  • Goldens decide. A change that alters any golden output needs a new evaluationVersion, a changelog entry, a new golden folder and reviewer sign-off; CI fails a PR that changes the current goldens without a bump. Previous goldens are kept so behaviour can be compared between versions.
  • New rules start as candidates. A grammar rule ships only after it passes the precision gate (≥ 0.90 † on ≥ 30 positive and ≥ 30 negative examples); the corpus grows with recogniser-captured examples, and a rule that later fails is demoted.
  • New metrics need validation and approval. The candidate acoustic metrics (pitch range, volume variation) stay hidden until SPK-01 validates them on the reference devices and the Product Owner approves them; they then enter the fixtures and goldens under a new version.
  • No model updates. Feedback, issues and tips stay deterministic functions of stored inputs; a generative or cloud model would need a new ADR, a privacy review and the Product Owner's authorisation (NG-01).

ARC-05 §10, §12; TST-01 §7.1–7.6; ARC-02 §9.4, §11.5.
